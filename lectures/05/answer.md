## 宿題

- 取り組んだレベル：基礎
- やったこと：
  - `app/config.py` の `RAG_TOP_K` を5から2に変更し、検索件数による回答品質と処理コストの違いを確認した。
- 比較した質問と、固定した条件：
  - 演習と同じLoRA・QLoRAの質問を使用。
  - モデルは `gemini-3.5-flash-lite`、対象資料と質問文は変更しなかった。

### 比較結果

| 指標 | TOP_K=5 | TOP_K=2 |
|---|---:|---:|
| 回答の正確性 | 正答 | 正答 |
| 引用ページ | p.51、52 | p.51、52 |
| 時間（秒） | 3.66 | 3.52 |
| 入力トークン | 3,028 | 1,741 |
| 出力トークン | 167 | 170 |
| モデル応答回数 | 2 | 2 |
| 生成API推定費用（USD） | $0.001326 | $0.000947 |

- `--trace`の比較：
  - 変更前後とも `search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` が1回呼び出された。
  - どちらも正しく回答し、第2回 p.51、52を引用した。
- 改善した例と、残る失敗・制約：
  - 入力トークンは約42.5%、推定API費用は約28.6%削減できた。
  - 一方、検索件数を減らすと、複数ページに根拠が分散する質問では必要な情報を取りこぼす可能性がある。
  - 各条件1回ずつの実験であり、応答時間や回答品質の安定性までは確認できていない。
- 気づき・疑問：
  - 検索件数を減らしても、今回は回答品質を落とさずコストを削減できたのが興味深かった。件数を増やせば精度が上がるとは限らないことを実際に確認できた。
  - 実運用ではTOP_Kを固定するよりも、質問の複雑さや検索結果の関連度によって取得件数を調整する方が合理的なのではないかと考えた。
