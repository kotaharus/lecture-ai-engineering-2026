#### 気づき・疑問

**1. 読みやすさとタスクの完了は異なる**

#02では、文章として読みやすくても、ユーザーが求める説明が完了していなかった。

**2. コードとLLMによる評価の使い分け**

| 評価対象 | 適した評価方法 |
|---|---|
| 講義回の表示形式 | コード |
| 講義回の実在確認 | コード・講義データとの照合 |

| 用語の意味的な正しさ | LLM |
| 誤った前提への対応 | LLM |
| 学習支援として適切なヒント | LLM |
| ツールの実行有無 | 実行ログ・コード |
| タスクの完遂性 | コードとLLMの組み合わせ |

決定論的に判定できる項目までLLMに任せる必要はない。一方、意味や文脈に依存する項目についてはLLMが有効である。

特にエージェントの場合、最終回答だけでなく、ツールの呼び出し履歴などの実行過程も評価対象に含める必要があると考えた。

**3. セキュリティと境界値の評価**

**4. 評価システム自体の耐障害性**

**5. 実験上の制約**

#### 問題の調査

| データセットID | 問題の概要 | 難易度の考察 |

| astropy__astropy-13033 | TimeSeriesの必須列を削除した際のエラーメッセージが不適切 | 例外処理と必須列のチェック処理を追えば対応できそう |
| astropy__astropy-14096 | 継承したクラスで属性を参照した際、例外に表示される属性名が正しくない | Pythonのpropertyや__getattr__の挙動を理解する必要がある |

参照したIssue：

- https://github.com/astropy/astropy/issues/12906
- https://github.com/astropy/astropy/issues/13009

個人的には2件目が最も取り組みやすそうである。過去のソフトウェア開発経験から考えると、不具合の再現手順が具体的に記載されているだけでも、原因調査の難易度はかなり変わる。

一方、1件目はPythonが書けるというだけでは解決が難しそうである。修正対象のライブラリがどのような仕様で設計されているのかを理解するところから始める必要がある。

LLMについても、コード生成能力だけでなく、既存のソースコードから必要な情報を探し出す能力や、影響範囲を特定する能力が問われると考えた。

#### 作成・検証方法

- Pythonの開発経験を持つ93人の開発者が検証に参加
- 元のSWE-benchから1,699件を抽出して評価
- 評価者の参加前に50件のサンプルを用いた事前テストを実施
- 1件につき3人が独立して評価
- 問題文やテストの妥当性を4段階で評価
- 3人のうち最も重大な判定を採用し、不適切な問題を除外
- 最終的に500件を採用

1,699件のうち1,199件が最終セットには含まれていない。ただし、品質上の問題による除外だけでなく、サンプリングによる非採用も含まれる。

#### 採点方法

- FAIL_TO_PASS：修正前に失敗していたテストが成功するか
- PASS_TO_PASS：修正前に成功していたテストが引き続き成功するか

通常のソフトウェア開発における不具合修正と回帰テストに近い考え方である。

#### 気づき・疑問

今回の演習では、コードで判定できる項目はLLMに任せず、コードで評価した方がよいと考えた。しかし、SWE-bench Verifiedの調査を通じて、コードで評価すれば正しい評価ができるという単純な話でもないことが分かった。

OpenAIが2026年2月に公表した再調査では、対象となった138件のうち59.4%に、問題文やテスト設計上の重大な問題が確認されている。93人の開発者が参加し、1件につき3人が確認したデータセットでも、このような問題が残っていたことは意外であった。

ソフトウェア開発でも、テストが通ったことと、要求仕様を満たしたことは必ずしも同義ではない。テストコード自体が間違っている可能性もある。

今回の演習でも、総合一致率が100%であるにもかかわらず、個別の評価基準では誤判定が発生していた。評価方法も規模も異なるが、評価結果の数値だけを見て判断することの危うさは共通していると思う。

また、今回自分が作成した10件の評価セットについても、別の人にレビューしてもらった場合、期待するふるまいや評価基準に対してどの程度意見が分かれるのか興味がある。

AIの開発ではモデルやエージェントの改善に注目しがちだが、評価データや評価器にも、通常のソフトウェアと同様に品質管理や継続的なメンテナンスが必要だと考えた。
